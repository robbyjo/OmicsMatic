# study.yaml field guide

Read [Start here](study-getting-started.md) first for a minimal complete contract,
file placement and commands. This page explains what you can add without making
the first example unreadable.

**Choose your shell:** use either the **PowerShell (Windows)** or the
**Bash (Linux/macOS)** version of each example. Keep the same terminal session
while following a walkthrough so its variables remain defined. On macOS, run
`bash` in Terminal before using the Bash examples if your default shell is zsh.
For steps that need review or filled-in YAML, stop at that point before continuing.

The [complete version-1 JSON Schema](../schemas/study-v1.schema.json) is the
field-by-field reference, including accepted names, types, ranges and enums.
The Java validator is authoritative:

**Windows (PowerShell):**

~~~powershell
java -jar $jar study validate study.yaml --check-files
~~~

**Linux / macOS (Bash):**

~~~bash
java -jar "$jar" study validate study.yaml --check-files
~~~

The schema's `$defs` contains named definitions such as `dataset`, `analysis`,
`assistance` and `bioinformatics`. Find those names in an editor, or use the
schema in a YAML-aware editor. Not every schema default is automatically written
into your draft: inspect `resolved-study.yaml` to see what the resolver used.
These guides target the current source build.


## Top-level structure

| Key | When to supply it | Contents |
| --- | --- | --- |
| `schema_version` | Always | Currently `1`. |
| `project` | Always | Stable `id`, readable `title`, study description; optional objective, investigators, organization, tags and policies. |
| `datasets` | Always as a key | Dataset descriptions and input paths. It can be empty for supported completed-results-only workflows. |
| `hypotheses` | Always | At least one scientific question, selected dataset IDs and its analysis configuration. |
| `cohorts` | For cohort-aware work | Cohort IDs, names, parent/subcohort relationships and relevant metadata. |
| `cohort_relationships` | When cohorts are compared or pooled | Independence, overlap, family or other dependence. Supply facts rather than inferring independence from different names. |
| `resources` | To control references or network access | Resource directory, download policy, offline policy and LD configuration. |
| `assistance` | Only for built-in AI assistance | Provider, model, credential-variable names or an encrypted-file reference, enabled purposes and approved sensitivity analyses. Omitted means disabled. |
| `analysis_requests` | For explicit additional registered requests | Request ID, type, relevant hypothesis and scientific reason. Often added through amendments. |
| `assumptions` | To record declared assumptions | Statement, source, affected entities and review status. |
| `_resolution` | Generated by OmicsMatic | Resolution metadata. Do not author this in a new study. |

Merge fragments into existing mappings. For example, add `data_policy` inside
the existing `project`, not as a second `project:` block. Duplicate YAML keys
are rejected. Likewise, each hypothesis has one `analysis` mapping.

## Describe each input dataset

A dataset needs a stable ID, a supported type and stage, and the file roles for
that stage. The useful optional metadata depends on the task.

| Information | Example keys | Why it matters |
| --- | --- | --- |
| Biological identity | `type`, `species`, `tissue`, `cell_type`, `assay` | Prevent inappropriate resource or assay substitutions. |
| Sampling | Dataset `cohort`, `visit`, `time`, `batch`, `specimen`; cohort `population` | Distinguish populations, visits and experimental structure. |
| Identifier system | `feature_id_type`, `genome_build`, `annotation_release`, `coordinate_system` | Match features and genomic resources without guessing. |
| Inputs | `files.matrix`, `files.phenotype`, `files.results`, `files.annotation`, `files.data_dictionary` | Tell the appropriate adapter what to read. Not every role applies to every stage. |
| Header translation | `columns` or the referenced dictionary | Map the actual source headers to the adapter's canonical fields. |
| Interpretation | `description`, `analysis_description`, `units`, `effect_contract` | Record what the estimates mean and whether pooling is defensible. |
| Provenance and eligibility | `source`, `provenance`, `feature_universe`, `metadata` | Preserve input lineage and the tested or eligible population. |

For example, add `species: human`, `genome_build: GRCh38` and the correct
annotation release only when they are true. An unknown value is a question to
resolve, not a prompt for AI to invent one. A gene symbol, transcript identifier,
probe and genomic variant require different interpretation and mappings.

For a processed matrix, the phenotype file must align to the matrix's participant
IDs, and the model needs correct outcome and covariate mappings. The
[full contracts and multi-phenotype examples](auditable-omics-pipeline.md)
explain those shapes; the
[study tutorial](study-pipeline-tutorial.md) gives task-specific extensions.

## Describe a hypothesis and select its work

~~~yaml
hypotheses:
  - id: H1
    description: Discovery effects replicate in an independent cohort.
    outcome: BMI
    covariates: [age, sex]
    inputs:
      discovery: [discovery-results]
      replication: [replication-results]
    analysis:
      mode: manual
      goals: [discovery_replication, meta_analysis]
~~~

This fragment refers to dataset IDs defined elsewhere in the contract.
For result-first inputs, listing covariates documents the study; it does not
refit the original model to add those covariates. Supply the source model and
effect scale, and verify both datasets measure compatible effects.

`analysis.mode: manual` keeps requested goals explicit. `auto` allows the
deterministic resolver to add eligible registered work. Both use the same
execution engine, and neither enables AI. Dependencies, QC, diagnostics and
reports may appear even when they are not explicitly named as goals.

Examples of goal families:

| Goal family | Representative goal names | Prerequisites to review |
| --- | --- | --- |
| Primary estimates and cohorts | `association`, `discovery_replication`, `meta_analysis`, `effect_comparison`, `cohort_overlap` | Appropriate inputs, models, effect scales and cohort dependence. |
| Enrichment | `gene_ontology`, `pathway_enrichment`, `ranked_gsea`, `gwas_enrichment` | Correct identifier mapping, tested universe or rank vector, gene sets and method-specific references. |
| Public context | `source_discovery`, `bioinformatics_investigation`, `literature_search` | Public labels/annotations, permitted network access and bounded queries. |
| Genetic inference | `mendelian_randomization`, `fine_mapping`, `colocalization` | Assay-matched QTLs, alleles, build, ancestry, LD and overlap declarations. |
| Networks and proteins | `network_analysis`, `network_modules`, `module_gene_ontology`, `protein_structure` | Appropriate matrices/graphs, module memberships, exact sequence and relevant resources. |
| Publication evidence | `finding_inventory`, `impact_assessment`, `candidate_prioritization` | Completed source evidence; AI impact assessment additionally needs configured assistance. |

The schema and `study operations --project .` expose the registered operation
catalog. A goal name is not a guarantee that its scientific inputs are available.
[Tool selection](study-tools-literature.md#choose-and-limit-the-tools) explains
how to avoid expanding the plan unintentionally.

## Reuse completed analyses

Put completed outputs under a stable directory such as `inputs/` and declare
each supported stage in `hypotheses[].analysis.supplied_results`.
Each entry needs an ID, typed `kind`, file roles, scientific `scope` and
`method`. Add column mappings, testing `family`, provenance and limitations
when applicable. These fields document what was actually done elsewhere.

The [complete import recipe](study-pipeline-tutorial.md#reuse-completed-analyses-and-run-missing-work)
covers meta-analysis followed by missing enrichment. The
[completed-study recipe](study-pipeline-tutorial.md#completed-analyses-through-manuscript)
covers broader reuse and manuscript preparation. Keep complete-family versus
selected-hit inputs explicit: enrichment and FDR cannot recover a missing
tested universe from a shortlist.

Supplying a primary completed stage can replace the corresponding native
calculation. Contributed or sensitivity evidence has a different role. Do not
describe a selected result as the complete primary analysis just to bypass a
missing-input gate.

## Reference resources and network policy

~~~yaml
resources:
  directory: project-resources
  network: offline
  downloads: deny
~~~

This is an offline resource policy, suitable when required resources are already
installed. Default source-build resource handling can acquire supported public
references automatically; inspect the resolved resource configuration before
approving a large study. LD resources can be large. See
[resource and LD behavior](bioinformatics-evidence.md#ld-and-automatic-reference-downloads).

A project can also constrain remote transmission:

~~~yaml
project:
  data_policy:
    llm:
      remote_transmission: deny_all
      remote_patient_level_data: deny
~~~

This is a fragment to merge with the existing project ID/title.
`deny_all` blocks remote AI assistance and the public-evidence adapter's
study-related queries. Generic reference installations have a separate resource
policy. Use `resources.network: offline`, `downloads: deny` and `--offline`
when an offline run is required. External tools and agents need their own controls.

To allow reviewed aggregate AI assistance, see the exact
[connection and disclosure examples](ai-connections.md).
Adding an API key never overrides a denied transmission policy.
